# AgendaVoice AI R4.2 — Motor universal de agenda

## Modelo temporal

- `branches.timezone` debe ser una zona horaria IANA válida, por ejemplo `America/Santiago`.
- Horarios de apertura, cierre y pausas se almacenan como `TIME` local semanal, con `weekday` lunes=0 a domingo=6.
- `appointments.starts_at` y `appointments.ends_at` se almacenan como `TIMESTAMPTZ` y se normalizan a UTC al recibir la solicitud.
- Las reservas que atraviesan medianoche no están soportadas en R4.2. Los horarios de verano se convierten con `zoneinfo`; los slots de horas locales inexistentes se omiten.
- La duración ocupada es `services.duration_minutes + services.buffer_minutes`.

## Herencia de horarios

La sucursal debe tener una configuración completa de siete días. Cada día es abierto con apertura/cierre o cerrado. Las pausas deben estar contenidas en el horario abierto.

Los profesionales y recursos pueden tener un horario específico de siete días. Si nunca se ha configurado un horario específico para ese profesional/recurso, hereda el horario y las pausas de la sucursal. Una vez configurado, su horario específico restringe la disponibilidad adicionalmente; no amplía el horario de la sucursal. Un `GET` que devuelve arrays vacíos indica que se hereda el horario de sucursal.

## Endpoints

| Método | Ruta | Función |
|---|---|---|
| POST | `/resources` | Crear recurso de una sucursal |
| GET | `/resources` | Listar recursos visibles |
| GET/PUT | `/branches/{id}/schedule` | Consultar/reemplazar horario y pausas de sucursal |
| GET/PUT | `/staff/{id}/schedule` | Consultar/reemplazar horario y pausas de profesional |
| GET/PUT | `/resources/{id}/schedule` | Consultar/reemplazar horario y pausas de recurso |
| GET | `/availability` | Consultar slots por día, servicio y recurso/profesional |
| POST | `/appointments` | Validar y crear reserva |
| POST | `/appointments/{id}/cancel` | Cancelar y liberar el intervalo |

Las rutas aplican el tenant autenticado por JWT, RLS y la asignación a sucursal del rol. El cliente no envía `tenant_id`.

## Prevención de doble reserva

1. La API toma advisory transaction locks para los IDs de profesional y recurso en orden determinista.
2. La API vuelve a consultar intervalos activos (`PENDING`, `CONFIRMED`) con semántica de intervalos semiabiertos `[inicio, fin)`.
3. PostgreSQL aplica `EXCLUDE USING gist` con `btree_gist` para profesional y recurso. La restricción es la garantía final contra carreras entre procesos; una colisión se devuelve como HTTP 409.
4. Cancelar cambia el estado a `CANCELLED`; las restricciones parciales dejan de considerar esa fila como ocupada.

La migración valida las zonas horarias IANA existentes, rangos de duración/buffer y estados; también realiza una comprobación previa de solapamientos existentes. Si detecta filas incompatibles, no instala las restricciones hasta que se corrijan.

## Pruebas

`tests/test_scheduling_r42.py` prueba reglas horarias, pausas, límites, validación de horarios semanales y una hora local inexistente por DST.

`tests/integration/test_postgres_scheduling_concurrency.py` lanza dos transacciones concurrentes contra el mismo profesional y, por separado, el mismo recurso. Debe ejecutarse con una base migrada y el rol runtime sin privilegios de superusuario ni `BYPASSRLS`.

## Límites deliberados

R4.2 no implementa feriados, excepciones por fecha, reprogramación, políticas comerciales de cancelación, reservas recurrentes, calendario externo ni reglas verticales avanzadas. Tampoco incluye un calendario visual en React.


Ejemplos de payload: `examples/branch_schedule.json`, `examples/appointment.json` y `examples/availability.txt`.
