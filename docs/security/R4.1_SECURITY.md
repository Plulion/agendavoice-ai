# AgendaVoice AI R4.1 — Seguridad y núcleo SaaS

## Alcance de esta versión

R4.1 implementa la capa inicial de identidad, autorización y aislamiento del núcleo SaaS. No declara el MVP completo ni sustituye una auditoría de seguridad independiente.

### Identidad y sesiones

- El registro crea tenant, usuario administrador, suscripción de prueba, índice de identidad y sesión renovable dentro de una transacción.
- Los correos se normalizan a minúsculas. La tabla `auth_identities` conserva únicamente `email`, `user_id` y `tenant_id` para resolver el tenant antes del login; no contiene hashes de contraseña ni datos de negocio.
- Tras localizar la identidad, la consulta del usuario y la verificación del hash ocurren con `app.tenant_id` establecido y RLS activo.
- Las contraseñas nuevas usan `bcrypt_sha256` mediante Passlib; los hashes bcrypt previos de R4.0 siguen siendo verificables durante la transición.
- Los access tokens duran `ACCESS_TOKEN_MINUTES`.
- Los refresh tokens tienen `REFRESH_TOKEN_DAYS`, JTI aleatorio, almacenamiento del hash del JTI y rotación de un solo uso. El token anterior queda revocado en la misma transacción.
- El frontend guarda ambos tokens en `sessionStorage` y renueva al recibir 401. Para producción se recomienda mover el refresh token a una cookie `HttpOnly`, `Secure`, `SameSite` y con protección CSRF.
- Logout revoca el refresh token presentado.

## Contexto transaccional de tenant

`set_tenant_context()` guarda el tenant autenticado en `Session.info` y lo establece con `set_config('app.tenant_id', ..., true)`. Un listener SQLAlchemy `after_begin` reaplica el GUC al comienzo de cada transacción de esa sesión. Esto corrige el caso en que un `COMMIT` elimina el valor local y una operación posterior (por ejemplo `refresh()` del ORM) necesita continuar bajo RLS.

El contexto se elimina al cerrar la sesión HTTP. No se usa `SET` de sesión persistente ni se confía en un `tenant_id` enviado por el cliente.

## RLS

Las tablas con datos tenant-scoped tienen `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY` y políticas `USING`/`WITH CHECK` basadas en `app.tenant_id`:

- `tenants` (política sobre `id`), `users`, `branches`, `customers`, `services`, `staff`, `resources`, `appointments`, `subscriptions`, `audit_logs`
- `refresh_sessions`, `user_branch_access`

La política histórica `app.auth_lookup` se elimina en R4.1. El rol runtime no recibe `BYPASSRLS` y no es propietario de las tablas. `auth_identities` es una excepción deliberada y limitada: índice global mínimo de login, sin contraseñas ni contenido de negocio. El runtime solo necesita `SELECT` e `INSERT` en esa tabla.

La tabla raíz `tenants` también lleva RLS. Para el registro inicial, el backend reserva un ID de la secuencia, establece `app.tenant_id` con ese ID y luego inserta la fila; así la política protege incluso la tabla raíz. El slug incorpora un sufijo aleatorio para evitar una consulta global de unicidad desde el runtime.

## Roles

| Rol | Alcance en R4.1 |
|---|---|
| `SUPER_ADMIN` | Administración total dentro del tenant al que está asociado. No implica acceso global cross-tenant. |
| `TENANT_ADMIN` | Administra usuarios, sucursales, catálogo, profesionales y operación de su empresa. |
| `BRANCH_MANAGER` | Opera profesionales y agenda solo en las sucursales asignadas. |
| `OPERATOR` | Crea clientes y reservas solo en sucursales asignadas. |
| `READ_ONLY` | Acceso de lectura a la operación de sus sucursales; no puede ejecutar endpoints de escritura. |

Las asignaciones se almacenan en `user_branch_access`, protegida también por RLS y con claves foráneas compuestas. Las relaciones de profesionales, recursos, reservas y auditoría también llevan tenant en sus claves foráneas, evitando referencias cruzadas incluso si se omite una validación de aplicación. Los usuarios creados por el endpoint `/users` requieren al menos una sucursal (máximo 100 por solicitud). No hay endpoint público para elevar roles ni crear otro `TENANT_ADMIN`.

## Auditoría

Se registran el alta de tenant, login, renovación, creación de usuarios, sucursales, servicios, profesionales, clientes y reservas. `GET /audit-logs` está limitado a administradores del tenant.

## Prueba real de aislamiento

Después de aplicar las migraciones, configurar `TEST_DATABASE_URL` con el usuario runtime `agendavoice_app` apuntando a una base de pruebas y ejecutar:

```bash
cd backend
alembic upgrade head
cd ..
TEST_DATABASE_URL='postgresql+psycopg://agendavoice_app:...@localhost:5432/agendavoice_test' ./scripts/test-postgres-rls.sh
```

La prueba verifica: cero filas sin contexto, visibilidad solo del tenant activo, persistencia del contexto tras `COMMIT`, rechazo de escrituras cruzadas por RLS, rechazo de referencias relacionales cruzadas por claves foráneas compuestas y ausencia de contaminación de conexiones. No debe apuntarse a producción.

## Límites conocidos / revisión antes de producción

- La aplicación usa JWT HS256; producción requiere secreto aleatorio robusto y rotación planificada.
- El refresh token se entrega en JSON y se guarda en `sessionStorage`; migrar a cookie HttpOnly antes de exponer el panel a usuarios reales.
- `auth_identities` es la única superficie global deliberada y requiere controles de tasa, monitoreo y revisión de amenazas.
- La desactivación de usuarios se respeta al validar access/refresh, pero todavía no existe endpoint administrativo para desactivar o cambiar contraseñas.
- La gestión de usuarios es alta/listado; edición, invitaciones y recuperación de contraseña quedan pendientes.
- La prueba PostgreSQL debe ejecutarse en el entorno Docker/DB real del proyecto; no se considera satisfecha por pruebas estáticas.
- La agenda R4.0 mantiene reglas simples; horarios laborales, pausas, cancelación, disponibilidad avanzada y pruebas de carrera completas pertenecen a R4.2.

## Continuidad R4.2 — Seguridad del motor de agenda

R4.2 conserva el contexto tenant y las claves compuestas de R4.1. Las nuevas tablas `branch_hours`, `branch_breaks`, `staff_hours`, `staff_breaks`, `resource_hours` y `resource_breaks` se crean con `ENABLE` + `FORCE ROW LEVEL SECURITY` y políticas por `app.tenant_id`. Sus relaciones con sucursal, profesional y recurso usan claves foráneas compuestas.

La migración agrega exclusiones temporales PostgreSQL para profesional y recurso (`EXCLUDE USING gist`, extensión `btree_gist`). La API mantiene advisory locks, pero la garantía contra doble reserva reside también en la base de datos. No se permite eliminar la política RLS ni sustituirla por un filtro de aplicación.
